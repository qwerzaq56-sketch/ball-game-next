# 원화 재현 리소스 제작·변환 제안

## 지형 제작 기준 정정 — 타일 분리와 레벨 구성 · 2026-10-06

**출처: 사용자 직접 제안·정정.** 풀이 많은 부분 / 풀밭 / 길을 별도 리소스로 제작하고 섞어서 레벨을 구성한다. 숲 텍스처만 확대해 규모감을 만드는 방식은 폐기한다. 아래 기준은 이전의 단일 지면 타일 제작·확대 방침보다 우선한다. 현재 숲 1600 월드 반복 크기는 후속 구현에서 공통 축척으로 교체할 대상이며, 이 문서 수정으로 코드가 변경된 것은 아니다.

### 공통 축척

- 6지역은 같은 월드 단위와 비교 기준을 사용한다. 기존 논리 셀 200, 제작 기준 모듈 400×400(2×2셀)을 유지한다. 출력 이미지 픽셀 수와 게임에서 차지하는 월드 크기는 별도 값이다. 고해상도 이미지를 만든다고 풀·돌까지 확대하지 않는다.
- 풀 한 포기·풀 군락·돌·나무의 기준 크기를 비교판에서 먼저 정한다. 시작 크기는 랜덤이므로 시작 캐릭터에 비례시키지 않고, 고정 size 40 / 100 캐릭터와 같은 줌에서 상대 크기를 확인한다(size는 반지름이 아니라 기존 게임의 크기 값).
- 큰 군락은 같은 크기의 요소를 넓게 조합해 만든다. 반복을 줄이기 위해 한 지역의 전체 텍스처를 늘리거나 다른 지역을 따라 확대하지 않는다. 큰 메타타일도 개별 요소의 축척은 유지한다.

### 숲부터 제작할 구성 요소

| 층 / 리소스 | 역할 | 1차 제작안 |
|---|---|---|
| 기본 바닥 | 이끼·흙의 낮은 대비 바탕, 빈 공간 | 2~3변형 |
| 풀밭 타일 | 낮고 성긴 풀, 기본 바닥이 드러남 | 3변형 |
| 고밀도 식생 타일 | 풀이 많은 군락 내부, 빽빽한 부분 | 3변형 |
| 길·공터 타일 | 흙이 드러난 통행 공간, 시각적 휴지부 | 바탕 2변형 + 직선/굽이/분기/끝 연결 규칙 |
| 전이 마스크 | 바닥↔풀밭↔군락↔길의 자연스러운 연결 | 공통 가장자리·코너·부분 패치 |
| 투명 식생·장식 | 풀 군락·관목·나무·돌의 독립 배치 | 풀 군락 3~5종부터, 크기·접지점 명시 |

수량은 제작 착수용 제안이다. 모든 풀을 독립 오브젝트로 만들 필요는 없지만, 바닥에 큰 나무·기능 오브젝트·먹이·이펙트를 구워 넣지 않는다. 장식 나무와 수호 고목 같은 기능 오브젝트는 별도 자산으로 유지한다.

### 섞어서 레벨 구성

단계는 **지역 구분 → 연결된 길·공터와 군락의 밀도 배치 → 타일 선택·전이 → 독립 장식 → 기능 오브젝트 → 효과** 순서다. 셀마다 독립적으로 랜덤 타일을 뽑아 얼룩을 만드는 대신, 몇 셀에 걸친 군락·빈 공간·완만한 길을 구성한다. 길 주변은 성기게, 군락 안쪽은 조밀하게 배치하고 규칙적인 격자·동일 간격 배열을 피한다. 연결 방향은 마스크와 조합으로 만들며, 광원이 구워진 그림을 무작정 회전하지 않는다.

길은 우선 시각적 공간 구분이다. 이동 보너스·충돌·새 게임 규칙은 추가하지 않는다. 장식 배치는 게임 난수와 분리된 좌표 기반 규칙을 사용한다. 기능 오브젝트의 효과 범위·판정 보정은 기존 승인 절차와 별도로 기록한다.

다른 지역도 같은 구조를 적용하되 표현은 다르게 한다: 초원은 흙/풀밭/꽃·풀 군락, 설원은 다져진 눈/눈밭/서리 군락, 사막은 평탄 모래/모래결/드문 식생, 화산은 암반/재/돌 군락, 호수는 잔잔한 수면/물결/수초·물가 패치. 호수의 시각적 통로를 육지로 해석하거나 용암 같은 실제 위험을 장식 타일로 대체하지 않는다.

### 제작·검증 순서

1. 원화의 색·광원·관찰각을 공유하는 숲 구성 요소를 만들고 공통 축척 비교판을 작성한다. ground-005 등 기존 시안·프롬프트는 보존하고 재분리·재제작 참고로 사용한다.
2. 같은 구성 요소로 성긴 공터 / 풀밭 / 조밀한 군락 / 굽은 길 장면을 조합한다. 규모감은 군락 면적과 공간 배치로 평가한다.
3. 실제 게임에서 작은·성장 캐릭터, 줌 0.5 / 1, 다른 지역과의 경계로 비교한다. 풀·돌의 크기 일관성, 길 연결, 타일 이음새, 광원, 몸 색·전조 가독성을 확인한다.
4. 숲 결과가 자연스러우면 나머지 5지역으로 확장한다. manifest에 픽셀 크기 / 월드 크기 / 피벗 / 층 / 밀도 유형 / 연결 규칙 / 원화·프롬프트 버전을 기록한다.

**후속 구현:** 숲 단독 1600 반복 확대를 공통 축척의 구성 요소·배치로 교체한다. 기존 다른 지역을 함께 확대하는 보정은 하지 않는다. 현재 런타임의 800/1600 반복 크기와 제작 기준 400 모듈을 연결하는 조합·캐시 방식은 구현 작업에서 검증한다. 리소스 제작 완료와 실제 적용 완료는 따로 기록한다.

## 판단

Canvas/SVG가 원화 표현을 원리적으로 못 하는 것은 아니다. 충분한 도형·패스·마스크로 복잡한 그림도 표현할 수 있다. 하지만 현재처럼 몇 가지 도형을 프로그램으로 조합하면 원화의 형태·색면·질감·구도 정보가 없어서 충실한 재현이 어렵다. 그림을 벡터풍으로 그렸다는 것과 파일이 벡터라는 것은 별개다. 지금 경계 페더링/무늬 추가만으로 원화와 같은 룩에 도달한다고 설명한 접근은 수정한다.

목표는 SVG 채택 자체가 아니라 실제 게임에서 원화와 같은 시각 언어를 재현하는 것이다. '완전히 동일'은 원본의 구성과 픽셀을 직접 보존하는 부분에만 기대할 수 있고, 새로운 지역/시점/상태를 생성하면 별도의 아트 검토가 필요하다.

## 가능한 방식 비교

| 방식 | 원화 충실도 | 장점 | 한계/비용 | 판단 |
|---|---|---|---|---|
| A. 원화 기준 이미지 리소스 제작, PNG/WebP로 직접 적용 | 원본을 보존한 영역은 가장 높음. 새 생성물은 검토 필요 | 복잡한 잎·바위·질감 유지, 현재 Canvas에 연결 가능 | 투명 가장자리·타일 이음새·축척·다수 자산 일관성 제작 필요 | 우선 추천 |
| B. 만든 이미지 → 기존 추적 엔진 → SVG 정리 | 단순 색면은 높게 맞출 수 있으나 자동 근사 | 크기 확대·색 교체·윤곽 수정 편리 | 패스 증가, 부드러운 질감/그라데이션 손실, 변환만으로 의미 레이어 복원 불가 | 일부 자산에 비교 실험 |
| C. 자체 변환 도구 개발 | 알고리즘/입력에 좌우, 완전 재현 보장 없음 | 프로젝트 전용 일괄 처리·팔레트·축척·검토 자동화 | 변환 엔진 자체를 처음부터 만들면 부담 큼 | B를 감싸는 제작 도구부터 |

**추천: 이미지 기반 배경·오브젝트 + 기존 벡터 캐릭터·전조·UI의 혼합.** 최종 렌더링은 캐시된 이미지로 통일할 수 있고, 원본 형식은 자산별로 선택한다. 현재 벡터 배경은 로딩 실패/아트 OFF용으로 보존한다.

## A. 실제 이미지 리소스 제작

승인된 concept-002-vector와 지역 컨셉을 참조해 숲의 큰 나무/잎 군락/바위/풀, 호숫가 조각, 지역별 바닥을 게임용으로 새 제작한다. 나무·바위는 투명 배경, 바닥은 반복 타일/큰 패치, 경계는 별도 알파 마스크로 구성한다. 기존 화면 전체를 배경으로 붙이면 공·먹이·HUD가 중복되고 지형 변화가 불가능하므로 그렇게 적용하지 않는다.

원화 부분을 그대로 추출하는 경우 원본의 손실/가림이 있는 영역은 별도 보완해야 한다. 생성 방식은 원화와 동일한 결과를 보장하지 않으므로 실제 게임 장면 비교가 승인 기준이다. 작은 캐릭터부터 풀·오브젝트가 크게 느껴지도록 자산의 월드 크기를 명시하며 성장에 따라 배경 리소스를 임의로 작게 다시 그리지 않는다.

assets/art-packs/<스타일>/ 아래에 terrain, foliage, landmarks, masks와 manifest를 둔다. manifest에는 원본·프롬프트·승인 상태·파일·월드 크기·피벗·장식/실제 기능 구분을 기록한다. 리소스 형식과 충돌/효과 판정을 분리한다. 기존 게임 난수 대신 좌표 고정 배치를 유지하고, 로드/디코드 후 캐시를 재사용한다.

## B. 이미지→벡터 변환

VTracer처럼 색상 이미지를 SVG로 추적하는 기존 엔진을 먼저 비교한다. Potrace는 기본적으로 흑백 윤곽 추적이라 컬러 그림을 그대로 맡기는 엔진으로 선택하지 않는다. 색상 분리와 재합성이 추가로 필요하다.

작업 순서: 투명 자산/원본 → 색 수·작은 잡티 정리 → 추적 → 패스/파일 크기 정리 → 동일 월드 크기로 PNG 직접사용 결과와 실제 화면 비교. 작은 풀이 SVG에서 더 자잘해지면 벡터 변환 실패로 판단한다. PNG를 SVG의 image 태그에 넣는 것은 포맷 포장일 뿐 진짜 벡터화로 보고하지 않는다.

나무/풀/바위/오아시스 네 대표 자산만 먼저 비교한다. 세밀한 배경 전체를 한 번에 변환하지 않는다. 추적 SVG는 게임에서 매 프레임 복잡한 패스를 그리지 않고 최초 로드 때 이미지 캐시로 그릴 수 있다. SVG를 선택해도 런타임 성능 이득이 자동으로 생기지는 않는다.

## C. 개발할 수 있는 제작 도구

변환 엔진을 처음부터 발명하기보다 기존 추적 엔진을 감싼 '원화 리소스 워크벤치'를 제안한다. 입력 이미지와 투명 여부·팔레트·잡티 제거·변환 정밀도를 설정하고, 원본/PNG/SVG를 나란히 비교한다. 배율0.5/1/2, 작은 공/성장 공을 동일한 월드 축척으로 겹쳐 보는 기능을 둔다.

일괄 변환, 파일 크기·패스 수·깨진 투명 경계 검사, 타일 반복 미리보기, manifest 출력, 생성 출처 기록이 최소 범위다. '자동으로 나무/풀의 의미를 이해해 레이어 복원', 자동 완벽 이음새, 자동 충돌 생성은 최소 범위에서 제외한다. 필요하면 사람이 레이어와 피벗을 지정한다.

## 최소 비교 제작과 완료 기준

1. 숲 한 장면을 대표 기준으로 정한다. 현재 게임 화면·승인 원화·동일 크기의 공을 함께 비교한다.
2. 나무/풀/바위/바닥 이미지 리소스를 만들고 실제 게임에 제한적으로 연결한다.
3. 일부 자산을 SVG로 추적한 비교본을 제작한다. PNG보다 비슷하고 편집 이득이 있을 때만 채택한다.
4. 실제 화면에서 형태·팔레트·식생 밀도·캐릭터 대비·작은 캐릭터 시점의 상대 크기·성장 시점·타일 반복·경계를 평가한다. 같은 위치/줌의 전후 캡처를 보존한다.
5. 데스크톱/모바일에서 로딩·메모리·프레임 비용을 측정하고 6지역으로 확대한다. 아직 측정하지 않은 성능/재현률 수치를 확정하지 않는다.

현재 권장 결정은 A부터 대표 숲 장면을 제작하고 B를 소규모로 비교하는 것이다. 변환 도구 개발은 실제 변환의 반복 필요성과 결과 품질이 확인된 후 진행한다. 본 문서는 제안이며 새 의존성 설치·변환 엔진 개발·기존 원화 삭제는 실행하지 않았다. 기존 수동 벡터 묘사 확대는 이 방법 검토 동안 보류한다. 이미 승인된 아트 작업은 제안 범위의 자료 조사·비교 준비를 이어갈 수 있다.

## 원화 일치 실험에서 얻은 제작 절차 · 잠정

## 실제 배치 후 룩 보정 — 사용자 직접 제안

리소스 생성·연결 다음에 **원화와 실제 게임 장면의 합성 룩 보정**을 필수 단계로 진행한다. 개별 오브젝트만 비슷한 것으로 완료 처리하지 않는다.

1. 같은 지역·카메라 위치·줌·캐릭터 크기로 원화와 실제 화면을 비교한다. 기준 시점은 원화의 비스듬한 탑뷰이며, 옆면을 없애는 것이 아니라 배경과 오브젝트의 관찰각·접지감·광원을 맞춘다.
2. **색보정:** 지역 팔레트에 맞춰 오브젝트의 색온도·명도·채도·그림자 대비를 조정한다. 캐릭터 종족색·공격 전조·위험 구분의 가시성을 유지한다. 원본을 보존하고 적용값 또는 보정본 버전을 기록한다.
3. **크기·비율:** 작은 캐릭터와 성장 캐릭터에 대한 상대 크기, 본체의 가로세로 비율, 줄기·수관·바위 높이, 이미지 여백과 접지 위치를 조정한다. 단순 확대보다 원화 장면 안에서의 비중을 기준으로 판단한다. 과도한 이미지 왜곡은 재제작으로 해결한다.
4. **이펙트·범위 표시:** 이펙트 색·강도·두께·투명도·지속 표현·그림 레이어와 범위 선의 색·두께·투명도·표시 조건을 함께 보정한다. 사용자 직접 정정: 보정된 오브젝트 크기를 기준으로 효과 반경과 실제 판정 범위도 직관적으로 이해되는 수준으로 변경할 수 있다. 본체가 접촉형인지 주변 영역형인지 기능에 맞춰 관계를 정하고, 표시 범위와 실제 판정 범위를 일치시킨다. 효과 대상·쿨다운·게임 난수는 별도 지시 없으면 유지한다. 필요한 위험/방향 정보는 보존한다.
5. 준비·수혜 후·활성/휴식, 줌0.5/1, 작은/성장 캐릭터, 여러 효과가 겹친 장면에서 재확인한다. 자연스러운 배치와 이동 공간도 함께 평가하고, 동일 조건의 전후 캡처·변경값·남은 차이를 과정 로그에 남긴다.

반복 순서: 원화 참조 → 리소스 제작 → 실제 배치 → 색/크기/비율/이펙트/범위 보정 → 합성 화면 비교 → 필요 시 리소스 재제작. 우선순위는 최종 화면의 자연스러움과 게임 정보의 가독성이다. 사용자 요청을 작업 절차에 반영한 것이며, 모든 항목의 보정 완료를 뜻하지 않는다.


### 크기와 효과 범위의 후속 조정 — 사용자 직접 제안·승인

초기 합성 보정에서는 본체의 시각적 크기와 효과 영역의 관계가 자연스럽게 읽히도록 효과 반경·접촉 판정을 함께 맞춘다. 본체와 범위를 반드시 같은 배율로 확대하는 규칙은 두지 않는다. 이후 튜닝은 (1) 본체 크기를 유지하고 범위·판정만 조정하거나, (2) 본체 크기와 범위·판정을 함께 조정하는 두 방식으로 진행한다. 범위 표시를 실제 판정과 함께 갱신하고, 작은/성장 캐릭터·두 줌·범위 안팎에서 직관성과 밸런스를 검증한다. 변경 전후 크기·반경·판정 규칙과 이유를 과정 로그 및 해당 규칙 카드에 기록한다. 이번 수정은 조정 권한과 절차의 승인이고, 개별 오브젝트의 새 수치는 구현·검증 단계에서 결정한다. 이전의 반경·판정 고정 조건보다 이 사용자 정정을 우선한다.
