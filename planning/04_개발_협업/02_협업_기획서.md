# 사용자 · Codex · Claude 협업 기획서

문서 버전: 0.2 / 개정일: 2026-10-02 / 상태: 공유 폴더 운영 기준 반영

## 1. 협업 목표와 역할

사용자는 원하는 경험과 방향을 결정하고 플레이 후 의견을 제공한다. Codex는 아이디어를 규칙·완료 조건으로 정리하고, 구현 결과와 피드백을 근거로 기획서를 수정한다. Claude는 실제 코드를 조사하고 구현·검증·커밋을 수행하며, 기술 제약과 결과를 보고한다.

Codex가 코드를 보지 않은 상태에서 구현 완료를 판정하지 않는다. Claude의 보고, 커밋 차이, 테스트·플레이 결과를 근거로 검토한다. 기술상 필요한 구조 변경은 Claude가 제안하고, 사용자 경험이나 원안 규칙이 달라지는 변경은 결정 기록을 남긴다.

## 2. 공유 폴더와 저장소

작업 영역은 `F:/GPT/ball-game/` 하나다. 역할과 공유 working tree 규칙의 기준은 [handoff/README.md](../../handoff/README.md)이며, 아래는 그 규칙을 기획 운영에 적용한 것이다.

```text
F:/GPT/ball-game/
  README.md
  ball-game-planning/          Codex: 기획 기준본, 별도 로컬 Git
    01_게임_기획서.md
    02_협업_기획서.md
    04_아이디어_백로그.md
    아이디어_로그.md
    기타 원안·제안·분석 메모
  ball-game-source/            Claude: 구현 기준본, GitHub 연결
    기존 코드·설정·GAME_DESIGN.md·BALANCE_NOTES.md
  handoff/
    README.md                 협업 운영 기준
    tasks/                    Codex: TASK 작성
    reports/                  Claude: 결과 보고
    log-codex.md               Codex만 추가
    log-claude.md              Claude만 추가
  ball-presentation/          사용자 지정 시에만 작업
```

기획 기준본은 `ball-game-planning/00_기준/01_게임_기획서.md`다. repo 문서는 실제 구현 사실을 적는다. 기획을 source의 docs로 복사하거나 이동해 기준본을 중복하지 않는다. 둘이 다르면 보고서의 ‘차이’에 기록한다. 우선순위는 사용자 지시 > 컨펌된 기획서 > 구현 사실 > 제안·초안이다. 구현 사실은 현재 동작의 근거이며 미승인 게임 규칙 변경의 근거가 아니다.

기획 저장소는 최초 커밋 `68fd310`에서 시작했으며 원격은 없다. source 저장소는 `https://github.com/qwerzaq56-sketch/ball-game`, 기본 브랜치는 master이며 최초 확인 HEAD는 `4e552a6`이다. 각 TASK는 실제 시작 시점의 커밋을 다시 확인한다. 기획 변경은 Codex가 관리하고, source의 브랜치·커밋·PR·push는 Claude가 담당한다.

## 3. 공유 폴더 작업 흐름

1. Codex는 자기 기획 저장소의 상태와 상대 로그를 확인한다. source를 조사할 때도 `git status`, `git log -3`을 먼저 읽는다.
2. Codex가 `handoff/tasks/TASK-xxx.md`에 담당·대상 파일·기준 기획·완료 조건을 작성한다. `담당:` 필드는 잠금이며 상대 담당의 TASK 대상 파일을 수정하지 않는다.
3. Claude는 TASK와 컨펌된 기획을 직접 읽고 작업한다. 결과는 `handoff/reports/TASK-xxx-result.md`에 쓰고 자기 로그에 추가한다.
4. Codex는 보고서와 코드 변경을 읽고 기획 대비 차이와 다음 수정안을 검토한다. 게임 규칙의 새 제안은 사용자 컨펌 전 기준본에 넣지 않는다.
5. 사용자가 병합·배포를 승인한다. 파일 작성만으로 상대 세션에 자동 알림이 전송되지는 않으며, 필요할 때 사용자가 TASK 경로를 전달한다.

각 로그는 append-only이며 자기 파일만 수정한다. 형식은 `YYYY-MM-DD HH:MM | 작업 | 대상 | 상태/미커밋 여부`다. 상세 결과를 로그에 반복하지 않고 TASK와 보고서로 연결한다.
## 4. 작업 단위

초기에는 별도의 관리 서비스를 추가하지 않고 `handoff/tasks/` 문서를 작업 원장으로 사용한다. GitHub Issue를 도입한다면 담당·진행 상태는 Issue로 옮기고 문서에는 규칙과 근거만 남긴다. 두 곳에서 상태를 별도로 관리하지 않는다.

작업 문서 형식:

```markdown
# TASK-001 — 작업 이름
상태: proposed / ready / implementing / review / done / blocked 중 하나
기준 코드 커밋:
기준 기획 문서·버전:
담당:

## 목적
어떤 플레이 문제를 해결하는가.
## 범위
구현할 규칙과 이번 작업의 경계.
## 완료 조건
관찰 또는 검증 가능한 조건.
## 검증 방법
시나리오, 시드, 측정 항목.
## 결정 필요 사항
사용자 경험에 영향을 주는 미정 항목.
## 결과
PR/커밋 링크, 보고서 링크, 남은 문제.
```

`ready`는 구현 가능한 규칙과 완료 조건이 정리됐다는 뜻이다. 사용자 승인이 반드시 필요한 항목은 명시하되, 통상적인 함수 분리나 설정 위치 같은 가역적인 기술 선택까지 승인 대상으로 만들지 않는다.

## 5. 브랜치와 커밋

브랜치는 기획 `docs/<task-id>-<topic>`, 구현 `feat/<task-id>-<topic>`, 수정 `fix/<task-id>-<topic>` 형태를 제안한다. 기획 저장소는 원격이 없으므로 현재 PR 대상이 아니다. source의 브랜치와 필요 시 PR은 Claude가 관리한다.

커밋 예:

```text
docs(TASK-001): define ecosystem baseline and metrics
feat(TASK-002): add prey and predator role assignment
fix(TASK-002): retain color rules during target selection
balance(EXP-001): adjust food spawn after simulation comparison
```

기획 변경이 먼저 필요하면 기획 저장소의 커밋 또는 미커밋 문서 버전을 TASK에 기록하고, source 구현 커밋과 보고서에서 참조한다. 두 저장소의 변경을 하나의 PR로 취급하지 않는다. 구현 중 기획 변경이 필요하면 Claude가 보고하고 Codex가 컨펌 절차를 거쳐 기획 기준본을 수정한다. 기획 의도와 실제 구현이 다르면 문서 또는 코드를 정정한 뒤 완료 처리한다.

커밋 수 자체를 목표로 하지 않는다. 기능을 중간에 깨뜨리는 임의의 분할보다 규칙·구현·검증의 관계를 읽을 수 있는 단위를 선택한다. 관계없는 변경은 함께 넣지 않는다.

## 6. 구현 결과 보고

Claude는 작업마다 다음을 보고한다.

- 구현한 행동과 기획 대비 차이.
- 변경 파일 및 PR/커밋 링크.
- 실행한 검증, 결과, 재현 방법.
- 사용한 설정값과 선택 이유.
- 남은 문제와 사용자 판단이 필요한 항목.

시뮬레이션 보고에는 시드·시간·설정과 실행 환경을 기록한다. 작은 요약과 대표 결과만 Git에 넣고, 대용량 원시 로그·영상은 필요 시 PR 첨부나 별도 저장소를 사용한다.

실험 보고서는 source 저장소 밖의 `handoff/reports/`에 둔다. source 커밋에 자동 포함된다고 전제하지 않는다. 실험 대상 코드 커밋·설정과 보고서 경로를 TASK 또는 PR에서 참조한다. 자기 자신의 미래 커밋 해시는 문서에 미리 쓰지 않는다.

## 7. 기획 수정 절차

아이디어 로그는 짧은 메모 형식으로 유지한다. 항목마다 `번호. 제목 · 날짜`와 핵심 내용 2~3개, 제안 출처, 컨펌·반영 버전을 적는다. 한 줄로 압축하지 않고 여러 줄로 나눠 읽기 쉽게 한다. 진행 표·반복 메타데이터·긴 검증 설명은 넣지 않는다. 상세 규칙·근거·검증은 기획서와 제안 문서에 둔다.

### 최소 기획 제출 시 자체평가

최소기획 제출 전 [전체 구현 우선순위](../00_기준/09_구현_우선순위_계획서.md)를 갱신하고 그 순서를 따른다. 미구현·부분 구현·미정 기능과 새 백로그를 목록에 포함한다. 앞선 기능의 규칙이 이미 컨펌됐다면 다음 미확정 기능의 최소기획을 제출한다. 개별 제안을 먼저 만들고 우선순위를 나중에 맞추지 않는다.

사용자 직접 제안(2026-10-02): 수치가 실제 플레이 시간에서 언제·얼마나 나타나는지, 의도한 긴장과 희소성을 유지하는지, AI 행동이 자연스러운 서사를 만드는지 평가한다.

이후 Codex는 각 제안에 다음을 포함한다.

1. **의도:** 만들려는 플레이 경험과 관찰 가능한 성공 조건.
2. **등장 시점·빈도:** 언제 시작되고 얼마나 자주 나타나는가. 평균뿐 아니라 빠른 사례·중앙값·등장하지 않는 사례를 기록한다.
3. **행동의 이유:** AI가 무엇을 보고 어떤 이익이나 위험에 반응하는가. 숨은 전역 정보나 강제 집결에 의존하지 않는지 확인한다.
4. **부작용:** 초반 생존, 성장 경로, 희소성, 기존 규칙에 주는 영향.
5. **근거 수준:** 코드 확인 사실, 계산, 가설, 플레이 실측을 구분한다. 측정 전 수치를 검증된 것처럼 쓰지 않는다.
6. **실험과 재검토:** 필요한 시나리오·지표·잠정 합격선, 실패 시 수정할 변수. 실험 목표도 제안임을 표시한다.

플레이 시간이 걸리는 검증은 초 단위 실행 시간이 아니라 게임 내 경과 시간으로 비교하며, 실제 사용자 플레이와 자동 AI 시뮬레이션의 결과를 구분한다. 사용자의 추가 평가 기준은 출처를 유지해 기록한다.

Codex는 구현에 필요한 최소 규칙·초기 수치·완료 조건을 스스로 작성해 제안 문서로 먼저 제출한다. 사용자 컨펌 후에만 기준 기획서에 반영한다. 기획 반영 후 아이디어 로그에 출처·원문·컨펌·반영 위치를 기록하고 해당 백로그 항목을 제거한다. 사용자 직접 제안한 원안은 **사용자 직접 제안**으로 표시한다. Codex 또는 Claude가 추가한 세부 규칙은 해당 AI의 제안으로 표시하며, 사용자의 컨펌과 출처를 혼동하지 않는다.

사용자의 체감 피드백은 상황과 기대 행동으로 정리한다. 예: ‘후반이 재미없다’ → ‘최상위 이후 먹이는 충분하지만 새로운 선택이 줄었다’. Codex는 현상, 원인 가설, 수정안, 확인 방법을 구분한다.

단순 수치 실험은 `handoff/reports/`의 해당 TASK 보고서에 기록한다. 확정된 규칙이나 사용자 경험이 바뀌면 기준 기획서를 수정한다. 중요한 방향 결정은 다음 형식으로 남긴다.

```markdown
# DEC-001 — 결정 주제
날짜:
상태: proposed / accepted / superseded
## 문제
## 결정과 이유
## 영향받는 규칙 및 작업
## 검증 결과 또는 재검토 조건
```

초안 제안은 사용자 결정처럼 기록하지 않는다. 미정 능력, 동족 관계, 새로운 성장 빌드처럼 게임 방향을 바꾸는 사항은 사용자 판단을 받아 반영한다. 구현 담당이 테스트용으로 넣은 값은 실험 값으로 표시한다.

## 8. 정정·충돌·완료 처리

역할 분리는 절대적이지 않고 **비율적**이다(사용자 지시 2026-10-03). Codex는 기획과 TASK를 주로, Claude는 source 코드·설정·repo 문서 및 보고서를 주로 맡지만 필요하면 서로의 영역을 직접 수정할 수 있다. 상대 영역을 고칠 때는 날짜·출처를 남기고 자기 로그에 기록한다. 사용자 의도나 컨펌된 규칙을 구현에 맞춰 바꾸는 경우에는 사용자 지시를 근거로 하거나, 지시가 없으면 사실 정정으로 처리하지 않고 보고서의 차이로 올린다. 같은 파일의 동시 편집만 피한다.

source는 같은 working tree를 사용한다. 세션 시작에 `git status`, `git log -3`, 상대 로그를 확인한다. 상대의 미커밋 변경은 건드리지 않는다. `checkout/reset/stash/clean` 전에 status를 확인하고 모르는 변경이 있으면 멈추고 사용자에게 묻는다. 실제 충돌이 발생하면 그때 worktree로 분리한다. 소유자는 변경하지 않는다. 필요한 경우에만 해당 경로의 safe.directory 예외를 사용한다.

master push/병합은 GitHub Pages 배포와 연결되므로 사용자 승인이 필요하다. force push, 삭제, 대규모 이동, 게임 방향 변경도 사용자 승인 대상이다. 승인을 요청할 때는 적용되는 handoff 규칙과 구체적 변경을 함께 설명한다.

작업 종료 시 커밋하거나 미커밋 변경을 자기 로그에 기록한다. 작업 완료는 코드 작성뿐 아니라 완료 조건 확인, 보고서의 변경 파일·검증·차이 기록, 남은 문제 분리를 포함한다. source의 커밋·브랜치·PR·push는 Claude가 수행하며 Codex는 이를 대신 수행하지 않는다.
## 9. 첫 협업 사이클

첫 구현 요청은 M0 조사다. Claude가 현재 흡수·전투·성장·AI·먹이 생성·카메라 구조와 실행 방법을 정리하고 기준선을 측정한다. Codex는 이 결과로 초안의 가정과 M1 완료 조건을 수정한다. 이후 역할 분류와 AI 행동부터 단계적으로 구현한다.

협업이 잘 작동하는 기준은 ‘기획 문서만 보고 구현 범위를 알 수 있는가’, ‘결과의 근거를 커밋과 보고서로 찾을 수 있는가’, ‘사용자 피드백이 다음 수정으로 연결되는가’다.


## 컨펌 대기 중 초안 병행

사용자 승인에 따라 컨펌을 기다리는 동안 다음 우선순위의 미승인 초안을 작성할 수 있다. 선행 초안 의존성을 명시하고 기준 기획서·로그에는 승인된 규칙만 반영한다. 컨펌이 도착하면 진행 중 초안을 저장하고 승인 반영부터 처리한 뒤 초안 작업을 재개한다. 이는 별도 에이전트 메시지나 자동 예약 실행을 허용하는 규칙은 아니다.

## 공개본 보존 — 사용자 추가 지시

트위터 공개된 기존/ball-game/ 링크는 유지하고 신규 게임은 별도 배포 대상/주소로 분리한다. 기존 master/Pages에 새 기획을 반영하지 않는다. TASK-002에서 실제 공개본·진행 중 변경·새 원격/작업영역을 조사하고 검토 가능한 준비를 제출한다. 권장 분리안과 실행 조건은 계획26을 따른다.
