# 규칙 카드 (rules/) — 전 도메인(P3)

2026-10-05 / 제안서 `04_개발_협업/27_기획구조_리팩토링_제안.md` P1~P3 / 사용자 승인("P1·P2·P3 진행해줘")

한 규칙 = 한 카드. 카드는 사람이 읽는 규칙 설명과 **기계가 확인하는 근거**를 함께 가진다. `tools/spec-trace.mjs`가 카드를 읽어 구현 저장소와 대조하고 `SPEC_TRACE.md`를 만든다(자동 생성, 수정 금지). 도메인 파일: `COMBAT`(전투·이동) · `ABS`(흡수) · `ECO`(생태계·직위·표시) · `AI`(AI 행동, 구승인 규칙) · `SPECIES`(종족 행동 특성) · `GROWTH`(성장·시야·생존) · `ABIL`(종족 능력) · `COMP`(동행) · `WORLD`(월드·지형·시대) · `CTRL`(조작) · `VIS`(표현) · `META`(측정). 구현 추인으로 승인된 규칙을 카드화한 것이며, 이 카드가 해당 규칙의 정본이다(도메인 문서 `00_기준/spec/`의 본문이 다르면 카드·카탈로그 §10이 우선). 수치 전부를 한 표로 보는 `BALANCE_SHEET.md`도 자동 생성한다.

## 규칙 ID
`R-<도메인>-<3자리>`. 도메인: ECO(생태계) · COMBAT(전투·이동) · ABS(흡수) · ABIL(능력) · COMP(동행) · WORLD(지형·시대) · CTRL(조작) · VIS(표현) · META(측정). **ID는 한 번 붙이면 바꾸지 않는다.** 규칙이 폐기되면 카드를 지우지 않고 상태만 `폐기`로 바꾼다. 카드를 쪼갤 때는 새 번호를 쓰고 원래 카드에 "분할됨 → R-…"를 적는다.
`00_기준/구현추인/28_구현추인_카탈로그.md`의 ID(R-COMBAT-001~005, R-ABS-001~004 등)와 같은 번호를 쓰며, 이 파일럿 카드가 그 항목의 정본이 된다(카탈로그는 색인으로 남는다).

## 카드 형식
```
### R-COMBAT-001 · 제목
- 규칙: 한두 문장. 사용자가 읽고 이해하는 문장.
- 상태: 승인 | 제안(사용자 미승인) | 후순위 | 설계만 | 폐기
- 출처: 사용자 지시/추인 날짜 · 근거 M번호 · 상세 문서
- 확인:
  - config attack.manualChargeSeconds = 0.9
  - symbol js/combat.js :: chargedAttackDistance
  - test tests/x.test.mjs :: 테스트 제목의 일부
- 변경 이력: (자유 서술, 도구는 읽지 않음)
```
확인 종류: `config <경로> (=|>=|<=) <값>`(구현의 `config/gameBalance.json` 값과 비교) · `skill <후보ID> <키> = <값>`(`js/skillCatalog.js` 능력 후보 수치) · `obj <ID> <키> = <값>`(`js/biomeObjectCatalog.js` 오브젝트 수치) · `symbol <파일> :: <식별자>`(함수·상수가 파일에 있는지) · `code <파일> :: <정규식>`(파일 안에 패턴이 있는지) · `test <파일> :: <제목 일부>`(테스트 제목에 있는지) · `file <경로>`.

## 상태·지표
- 카드 상태(사람이 정함): **승인**(사용자가 승인한 현재 규칙), **제안**(아직 사용자 승인 전 — 추적 점수에 포함하지 않음), 후순위, 설계만, 폐기.
- 추적 결과(도구가 계산): **구현됨**(config·symbol·file 확인이 전부 통과) · **검증됨**(연결한 테스트가 전부 존재) · **상충**(config 수치가 카드와 다름) · **확인 실패**(식별자·경로·테스트 제목을 못 찾음).
- 지표: A1 구현율, A2 검증율, A5 상충 수, 테스트 미연결 카드 수.
- **한계:** 도구는 존재와 수치만 본다. 테스트가 통과하는지, 규칙을 올바르게 구현했는지는 `node --test`와 사람이 본다. 수치가 없는 규칙(행동 서술)은 symbol·test 확인만 가능하다.

## 실행
```
node tools/spec-trace.mjs   --impl <구현 저장소 체크아웃 경로> [--commit <표시용 커밋>]   → rules/SPEC_TRACE.md
node tools/balance-sheet.mjs --impl <구현 저장소 체크아웃 경로> [--commit <표시용 커밋>]   → rules/BALANCE_SHEET.md
```
종료 코드 1이면 상충 또는 확인 실패가 있다. 도구는 기획 저장소(`rules/`가 도구 옆)와 구현 저장소(`planning/rules/`, 저장소 루트에서 `--impl .`) 어느 쪽에서든 실행된다.

## 코드·테스트 ID 태그 (P3 시행)
새로 만들거나 바꾼 규칙의 코드 주석에 `// R-COMBAT-001`, 테스트 제목에 `R-COMBAT-001`을 적는다. 도구가 `js/**`·`tests/**`에서 ID를 찾아 카드별 태그 수를 보고하고, 카드에 확인 줄이 없을 때는 태그를 구현·검증의 근거로 인정한다. 카드의 `symbol`/`test` 줄을 손으로 유지하는 비용을 줄이는 장치다.

## 운영 규칙
- **카드는 규칙의 정본**이다. 수치를 바꾸면(카드의 `config`/`skill` 값과 달라지면) 도구가 상충으로 알려 준다. 의도적 변경이면 카드의 값과 `변경 이력`을 고치고 사용자에게 "기존 승인 규칙 변경"으로 보고한다.
- 새 규칙은 상태 `제안`으로 카드를 만들고 사용자 승인 뒤 `승인`으로 바꾼다.
- `SPEC_TRACE.md`·`BALANCE_SHEET.md`는 생성물이다. 직접 고치지 않는다. 수치의 의도 설명은 `balance-intent.json`(경로 접두어 → 한 줄)을 고친다.
- 구현 저장소의 `planning/rules/`는 클라우드 작업용 사본이다. 정본은 기획 저장소 `rules/`이며 클라우드가 고친 카드는 마일스톤 보고 때 기획 쪽에 반영한다.
