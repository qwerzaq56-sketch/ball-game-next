# 클라우드 작업 지침 추가 — 규칙 카드와 자동 추적 (P3, 2026-10-05)

이 지침은 `CLOUD_BRIEF.md`와 `IDEAS_2026-10-03.md`에 **추가**된다. 충돌하면 이 문서가 더 최신이다.

## 무엇이 추가됐나
- `planning/rules/` — 승인된 규칙 78개를 **규칙 카드**로 만든 것(전투·흡수·생태계·능력·동행·월드·조작·표현·측정 9개 도메인). 형식·운영 규칙은 `planning/rules/README.md`.
- `tools/spec-trace.mjs` — 카드를 코드와 자동 대조(수치·함수·테스트 제목 존재). `tools/balance-sheet.mjs` — 조절 수치 전부와 의도를 한 표로 생성.
- 이 브랜치(`codex/spec-sync`)는 `codex/cloud-next-m4`의 마지막 커밋(`2fd3bd8`)에서 **새 파일만** 추가했다. 기존 파일은 바꾸지 않았으므로 작업 브랜치에 그대로 합쳐도(merge 또는 cherry-pick) 충돌하지 않는다. main에는 합치지 않는다.

## 매 마일스톤에서 할 일
1. **시작 전** `planning/rules/README.md`를 읽고, 바꾸려는 기능과 관련된 카드(`planning/rules/*.md`의 `R-도메인-번호`)를 확인한다. 카드 `규칙` 줄이 현재 승인된 규칙이다.
2. **구현 중** 규칙을 새로 만들거나 바꾸면 해당 코드 주석에 `// R-COMBAT-001` 같은 **ID 태그**를, 테스트 제목에 같은 ID를 적는다(`npm test` 제목 예: `R-COMBAT-001 충전 공격 …`).
3. **마일스톤 끝에** 아래를 실행하고 결과 요약(카드 수·구현 확인·검증·상충·확인 실패·태그 카드 수)을 `CLOUD_REPORT.md` 해당 마일스톤 항목에 한 줄로 적는다.
   ```
   node tools/spec-trace.mjs --impl . --commit <커밋> --out /tmp/SPEC_TRACE.md
   node tools/balance-sheet.mjs --impl . --commit <커밋> --out /tmp/BALANCE_SHEET.md
   ```
   생성 파일은 커밋하지 않는다(`--out`으로 저장소 밖에 쓴다).
4. **상충(수치가 카드와 달라짐) 처리**
   - 의도한 조정이면: 해당 카드의 `config`/`skill`/`obj` 값과 `변경 이력`을 고치고, 보고서에 **"기존 승인 규칙 변경"** 항목으로 변경 전후 값·이유·근거 측정치를 적는다. 사용자가 아직 승인하지 않은 변경이면 그 카드의 `변경 이력`에 "미승인 변경(마일스톤 번호)"이라고 적는다. 카드 상태는 `승인`으로 둔다(상태는 사용자가 정한다).
   - 의도하지 않은 변화면: 코드를 되돌린다.
5. **새 규칙**(카드가 없는 새 기능)은 해당 도메인 파일에 카드를 추가한다. `상태: 제안`, 근거(`config`/`symbol`/`test`)를 채운다. 사용자 승인 전에는 `승인`으로 바꾸지 않는다.
6. 카드의 `test` 확인 줄에는 **실제 테스트 제목의 일부**를 넣는다. 제목을 바꾸면 카드도 같이 고친다(도구가 확인 실패로 알려 준다).

## 하지 말 것
- `SPEC_TRACE.md`·`BALANCE_SHEET.md`(생성물)를 직접 편집하거나 커밋하지 않는다.
- 카드에서 `폐기`가 아닌데 카드를 지우지 않는다. ID는 바꾸지 않는다.
- 도구가 통과한다고 규칙이 맞게 구현됐다는 뜻은 아니다. 도구는 수치·함수·테스트 제목의 존재만 본다. `npm test`는 별도로 통과해야 한다.
- 기획 정본(기획 저장소 `rules/`)은 사용자 로컬에 있다. 이 저장소의 `planning/rules/`는 클라우드용 사본이며, 고친 카드는 마일스톤 보고 때 사용자 쪽이 정본에 반영한다. 사본에 없는 도메인 문서(`00_기준/spec/`, 구현 우선순위)는 이 저장소에 없다.
